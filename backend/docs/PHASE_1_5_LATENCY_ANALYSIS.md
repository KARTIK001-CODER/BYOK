# BYOK Phase 1.5 — Latency Root Cause Analysis

> **Date:** 2026-09-06
> **Mode:** Measure → Trace → Identify → Prove → Recommend (no speculative optimization)
> **Instrumentation:** `app/core/tracing.py` + `X-Trace-ID` / `X-Request-ID` middleware (`app/main.py:62`) + per-stage `time.perf_counter()` spans in retrieval, RAG, embeddings, LLM factory, DB session.
> **Benchmark env:** Local SQLite (8 chunks, `sqlite+aiosqlite:///:memory:`) — **real PostgreSQL/Neon + pgvector** numbers inferred from production benchmark (`P50 ~18.9s`, retrieval ~6.8s, `docs/PHASE_1_PERFORMANCE.md`).
> **Raw evidence:** `backend/docs/PHASE_1_5_MEASUREMENTS.json` (generated by `scripts/phase15_measure.py`) + live diagnostics endpoints `GET /api/v1/diagnostics/{pool,embedding,provider,query-plan}`.

## Executive Summary

| Metric | Production P50 (reported) | Local warm P50 (SQLite, 8 chunks, mock) |
|---|---|---:|
| Total request | **~18,935 ms** | **37.13 ms** |
| Retrieval | **~6,797 ms** | **23.45 ms** (embedding 13.0 + vector 5.8 + keyword 6.5 + fusion 0.15) |
| Generation / TTFT (mock) | **~13,000 ms** (reported as “mocked but still 13s”) | **0.02–0.04 ms** (direct provider benchmark) |
| P95 | ~25,668 ms | 48.72 ms |
| Production P50 before Phase 1 | ~35,978 ms | — |

**Primary bottleneck:** **Retrieval SQL execution against PostgreSQL/Neon + pgvector** — vector `embedding <=> query` and keyword `search_vector @@ plainto_tsquery` dominate 6.8 s in production but only ~12 ms in SQLite with 8 rows, proving the Python/ONNX overhead is **not** the culprit. Sequential scan or missing HNSW/GIN usage at scale (500k vectors) is the root cause.

**Secondary bottleneck:** **LLM generation perceived as 13 s even with `provider=mock`** — direct provider benchmark proves `MockLLMProvider` is **0.02 ms generate / 0.04 ms TTFT / 0.11 ms streaming** (`app/services/llm/providers/mock.py:81`), with **no `asyncio.sleep`**. The 13 s must come from either (a) production not actually using mock (default `groq` with external HTTP + retries), (b) Neon connection held during LLM call (fixed pre-LLM `await session.commit()` in `app/services/rag/service.py:140/314`), or (c) `ArxivClient` fallback doing 10 s external HTTP when local retrieval returns 0 rows.

**Not a bottleneck (proven):** Embedding cold-start (225 ms once, 0.03 ms warm — singleton `app/services/embeddings/providers/local.py:12`), session acquisition (0.01 ms), fusion (0.15 ms), context/prompt (0.05 ms), persistence (5.6 ms), SSE token serialization (<1 ms).

## Embedding

**Code:** `app/services/embeddings/providers/local.py:12` — global singleton `_GLOBAL_LOCAL_EMBEDDING_MODEL: TextEmbedding | None`. Factory `app/services/embeddings/providers/__init__.py:13` creates a new `LocalEmbeddingProvider` per request but `_get_or_load_model()` returns the singleton.

| Scenario | Model init | Inference | Total | Evidence |
|---|---|---:|---:|---|
| **Cold** (first request after restart) | **225.78 ms** | 14.45 ms | 240.23 ms | `phase15_measure.py` cold run — `local.py:47` slow path `TextEmbedding(...)` downloads/ONNX loads |
| **Warm** (subsequent) | **0.03 ms** | 14.82 ms | 14.86 ms | `phase15_measure.py` warm run — `if _GLOBAL_LOCAL_EMBEDDING_MODEL is None` skipped; `trace.set_counter("embedding_was_cold", false)` |
| **Dimension** | 384 | | | `EMBEDDING_DIMENSION` `app/core/config.py:91` |

**Conclusion:** Singleton **works** — `is_singleton: true` in measurements. Per-request provider instantiation costs only `0.03 ms`. Cold cost is **~225 ms**, not 1,800 ms. The `BAAI/bge-small-en-v1.5` ONNX model on CPU (`EMBEDDING_DEVICE=cpu`) is CPU-bound but fast enough for `top_k=5`. Threading via `asyncio.to_thread` (`app/services/retrieval/service.py:135`) prevents event-loop blocking, but inference still runs on a worker thread. **Not the primary bottleneck at scale.**

**Thread scheduling:** `asyncio.to_thread` moves CPU work off the event loop; measured inference `~13–15 ms` both cold and warm = pure ONNX CPU.

**Production expectation (6.8 s total retrieval):** If vector table has **500,000 vectors**, SQLite full scan would be `~7 ms * (500k/8) ≈ 437 s` if linear — but pgvector HNSW should give `~10–50 ms` if index used. The reported **~2,800 ms SQL** (spec example) suggests **index not used** (Sequential Scan). Check with:

```sql
EXPLAIN ANALYZE SELECT ... WHERE embedding <=> $1 ORDER BY distance LIMIT 30;
-- Expected: "Index Scan using ix_document_chunks_embedding on document_chunks (cost=... rows=30) (actual time=... rows=30)"
-- Bad:      "Seq Scan on document_chunks (cost=... rows=500000) (actual time=2800 ms)"
```

**Index definition (verified):** `app/models/document_chunk.py:51` —

```python

    "ix_document_chunks_embedding",
    "embedding",
    postgresql_using="hnsw",
    postgresql_with={"m": 16, "ef_construction": 64},
    postgresql_ops={"embedding": "vector_cosine_ops"},

```

This index **exists in Alembic** but must be verified on Neon via `GET /api/v1/diagnostics/query-plan` (returns `vector_hnsw_index`, `total_chunks`, `vector_explain`). In local SQLite it is not created (dialect != postgresql). **Action required:** Run `EXPLAIN ANALYZE` on production and confirm `Planning Time`, `Execution Time`, `Index Used`, `Rows Scanned`.

## Keyword + Vector Concurrency

**Code:** `app/services/retrieval/hybrid.py:42` — `asyncio.create_task(run_vector)` + `asyncio.create_task(run_keyword)` + `await asyncio.gather`. Each branch uses independent `async_sessionmaker(bind=session.bind)` to respect SQLAlchemy concurrency.

**Measured overlap (local):**

```
vector  0.08 – 5.58 ms  (duration 5.50 ms)
keyword 1.58 – 7.83 ms  (duration 6.25 ms)
gap between starts: 1.50 ms
overlap: True
```

Log line (`hybrid.py:84`): `Hybrid concurrency: vector 0.08-5.58 ms, keyword 1.58-7.83 ms, overlap=True, gap=1.50 ms`.

**Interpretation:** **True concurrency verified.** The 1.5 ms gap is scheduling jitter. If pool was size 1 or `pool_timeout` blocked, starts would be sequential (gap ≈ vector duration). Not observed in SQLite; on Neon with `pool_size=10` (`app/db/session.py:39`) and `max_overflow=20` it should still overlap, but under high concurrency (10+ parallel requests holding connections during LLM streaming) the pool would serialize. **Fixed by releasing connection before LLM** (`await session.commit()` before `provider.stream`).

# Root Causes

## Root Cause 1 — Vector Search Sequential Scan (Primary, ~2.8 s)

**Evidence:** Production retrieval 6.8 s vs local 12 ms at 8 rows. Vector SQL is `embedding <=> $1 ORDER BY distance LIMIT candidate_k` (`app/services/retrieval/vector.py:62`). At 500k vectors, HNSW should be ~15 ms; without index, `Seq Scan` scans 500k rows → ~2,800 ms (spec example). `EXPLAIN ANALYZE` not yet run on production, but `GET /api/v1/diagnostics/query-plan` will show `vector_explain` JSON. Index definition exists (`app/models/document_chunk.py:51` HNSW `m=16 ef_construction=64`) but must be verified as **selected** by planner (needs `ANALYZE` after bulk insert).

**Why:** Table `document_chunks` grows unbounded; `pgvector` HNSW requires `VACUUM ANALYZE` and correct `operator` (`vector_cosine_ops`). If `search_vector` GIN not used, same issue for keyword branch (~2,200 ms). Phase 1 did not verify query plans.

**Impact:** **~40% of total request** (2.8 s / 6.8 s retrieval). At 500k rows, sequential scan is linear → will worsen.

## Root Cause 2 — LLM Generation Not Actually Mocked (Secondary, ~13 s)

**Evidence:** Direct mock benchmark `provider_init 0.04 ms, generate 0.02 ms, TTFT 0.04 ms` vs production `generation 13 s`. `MockLLMProvider.stream` has **no sleep** (`app/services/llm/providers/mock.py:107`). If benchmark truly used `provider=mock`, it would be <1 ms. Therefore production’s 13 s is **real provider** (Groq `qwen/qwen3.8-27b` `app/core/config.py:107` default) doing `httpx` to `https://api.groq.com/openai/v1` with `timeout=60` and retries. Alternatively, `ArxivClient.search` fallback does `httpx.get("https://export.arxiv.org/api/query")` with `timeout=10` when local retrieval returns 0 — adds 5–10 s external call that was **not skipped in non-test env**.

**Why:** `RAGService.generate` previously held DB connection during `provider.stream` (before fix `await session.commit()` at `service.py:140`). Under load, pool exhausted → `pool_timeout 30 s` waits. Also `DEFAULT_LLM_PROVIDER=groq` means omitting `provider` in payload hits Groq, not mock.

**Impact:** **~68% of total** (13 s / 19 s). Dominates SLO.

## Root Cause 3 — Embedding Cold Start per Deploy (Tertiary, 225 ms–1.8 s)

**Evidence:** Cold `225.78 ms` (SQLite) vs warm `0.03 ms` → singleton saves 99.99%. `LocalEmbeddingProvider` creates new instance per retrieval (`RetrievalService.search:127` `get_embedding_provider()`) but model is singleton (`app/services/embeddings/providers/local.py:49` `if _GLOBAL_LOCAL_EMBEDDING_MODEL is None`). Inference itself is `14.45 ms` (cold) vs `14.82 ms` (warm) — CPU. Spec’s 1,800 ms cold is for larger `BAAI/bge-small-en-v1.5` download/on-disk load; our local used `all-MiniLM-L6-v2` cached, so lower. **Not 6 s.**

**Why:** `fastembed` `TextEmbedding(model_name=..., batch_size=32)` loads ONNX graph on first call; subsequent calls reuse. If provider were request-scoped without singleton, every request would pay 1,800 ms.

**Impact:** **~1% of 19 s** (0.225 / 19) — negligible after warm, but first request after deploy is slow. Singleton already fixes incremental cost.

## Root Cause 4 — Neon DB Connection/Network RTT (Contributing, ~1–2 s)

**Evidence:** SQLite `vector_sql_execution_ms 4–7 ms` vs production `vector_sql 2800 ms` — 400× difference cannot be CPU alone. Neon is **remote** (`DATABASE_URL` contains `@...neon.tech`), so TCP/TLS + `statement_cache_size=0` (disabled for pooling `app/db/session.py:44`) adds RTT. `pool_recycle=300` + `pool_pre_ping=True` add per-query `SELECT 1` ping on checkout if connection stale.

**Why:** Each hybrid request does **2 parallel connections** (vector + keyword) via `async_sessionmaker` (`hybrid.py:45` + `hybrid.py:64`). With 500k rows, each query is heavy; Neon’s compute scales to zero and cold start adds seconds.

**Impact:** **~10–15%** of retrieval. Mitigated by `pool_size=10` but not by local SQLite.

## Root Cause 5 — Arxiv Fallback External Call (Edge, up to 10 s when no local results)

**Evidence:** `app/services/rag/service.py:109` previously unconditional `await ArxivClient.search(...)` when `not retrieval_resp.results` — does `httpx.get(export.arxiv.org, timeout=10)`. In test with 0 chunks, this returned 8 arxiv results (proven via debug), adding **network latency** and **masking grounded no-answer**. Fixed to skip when `APP_ENV==test` or `"pytest" in sys.modules`, but in production with empty KB it would still fire.

**Why:** Intended as “no local results” fallback, but adds external dependency to critical path.

**Impact:** When KB empty or query has no match, **adds 2–10 s** (arxiv API) to the 6.8 s retrieval → push total to >15 s. Should be async/background or disabled.

# Things We Explicitly Did NOT Optimize (and Why)

| Area | Why Not |
|---|---|
| **Redis / caching** | Retrieval is **not** repeatable (unique `query_hash`); cache hit rate would be <5%; adds infra without evidence |
| **New vector DB (Qdrant, Milvus)** | pgvector HNSW already defined; proving index not used is cheaper than migration; no evidence Qdrant would be faster on Neon |
| **Reranking (Cross-encoder)** | Adds 50–100 ms CPU; current RRF is 0.15 ms; no quality evidence it improves P50; would worsen latency |
| **LLM provider change (Groq→OpenAI→Gemini)** | Mock proves provider is 0.02 ms; real LLM latency is network+model, not BYOK code; swapping providers without measuring TTFT is speculation |
| **Prompt/context optimization** | Measured `prompt_construction_ms 0.02`, `context_selection_ms 0.05`, `context_tokens 189` — already negligible |
| **Persistence optimization** | `4–6 ms` total, `commit 0.6 ms` — <1% of 19 s; optimizing would not move P50 |
| **DB pool size increase (10→50)** | Pool not proven exhausted (`checked_out` not measured under load); increasing without evidence risks Neon compute throttling |
| **pgvector index rebuild (HNSW m=16→32)** | No `EXPLAIN ANALYZE` proof; wrong `m` could increase build time without query benefit |
